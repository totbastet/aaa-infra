## Выбор фреймворка
Для реализации я выбрала фреймворк fastapi, потому что это сейчас стандарт для реализации ML сервисов на Python. Он является одним из самых быстрых, а также поддерживает асинхронность.

## Выбор метрик

Для инференс-сервиса я выбрала три метрики:

1. Latency P50/Р95/Р99

Она показывает время, которое проходит от момента отправки запроса пользователем до получения ответа. В отличие от среднего арифметического, на которое сильно влияют одиночные аномально долгие запросы, перцентили позволяют увидеть реальную картину для разных групп пользователей.
Я решила использовать все 3 перцентиля, потому что каждый из них помогает по-разному проанализировать ситуацию.

- Р50 - это медиана, она показывает типичный опыт пользователя. 

- P95 показывает задержки, которые случаются регулярно. Если P95 плохой, значит, каждый 20-й пользователь видит задержку, сервис не справляется с нагрузкой.

- Р99 показывает экстремальные выбросы. Если P99 плохой, а P95 хороший, то в системе есть редкие, но тяжелые проблемы, а значит такие запросы могут блокировать ресурсы сервиса надолго. Это может привести к тому, что сервис перестанет справляться с основным объемом запросов.

Также время работы rubert-mini-frida сильно зависит от длины подаваемого текста. P95 покажет скорость обработки обычных предложений, а Р99 - длинных текстов.

Считается, что ответ в пределах 200 мс моментальный, а 500 мс для пользователя уже является ощутимой задержкой. rubert-mini-frida специально облегчена для более быстрой работы, поэтому целевой порог выбрала Р95 < 200 мс.

Если порог нарушен, то можно выделить больше ядер или запустить несколько экземпляров сервиса. Если при этом Р99 остается в норме, то буду накапливать запросы и обрабатывать их вместе за один проход. Если же Р99 тоже велик, нужно жестче ограничить max_length в токенизаторе.

2. Throughput (RPS)
Количество запросов, которые сервис успешно обрабатывает за одну секунду.
Показывает насколько хорошо приложение масштабируется и какой поток пользователей выдержит один контейнер. Для ML-сервисов это обычно самое узкое место, так как нейросети сильно нагружают процессор.

Для сервиса на одном ядре CPU я выбрала порог RPS > 10.

Если порог нарушен, то можно создать несколько экземпляров сервиса или использовать батчинг и обрабатывать по несколько запросов за один проход.

3. Memory Usage

Объем оперативной памяти, который занимает процесс внутри Docker. Показывает стабильность сервиса. Если память будет постоянно расти, сработает OOM Killer, и операционная система просто уничтожит контейнер.

Приемлемый порог < 1.5 ГБ. Модель rubert-mini-frida сама по себе небольшая (160 МБ), но библиотеки PyTorch и Transformers потребляют довольно много ресурсов при инициализации.

Если порог нарушен, то нужно проверить код на утечки памяти, например, не копятся ли старые тензоры в глобальных списках. А также можно очищать кэш PyTorch после тяжелых операций.
